# ReasoningForge：GRPO 训练监控指标字典

本文按当前 **Qwen2.5-1.5B-Instruct + LoRA + GSM8K 数值奖励**解释指标。「已有·训练」写入 `runs/<实验名>/metrics.jsonl`；「已有·开发」在配置 `dev_data_path` 与 `eval_steps` 后写入 `dev_metrics.jsonl`；「已有·评估」可单独运行 `evaluate.py`；「手工」需查看保存的回答；「未实现」代表代码不会自动计算。项目尚未进行正式 GSM8K 训练，因此这里是观测方案，不是实验结果。按要求未加入显存峰值、累计墙钟时间和 GPU 小时统计。

先约定：`B` 是每次采样的题目数，`G` 是每题生成的回答数，当前 1.5B 配置为 `B=1、G=4`；`R` 是回答 token 长度。一个题目连同 `G` 个回答叫一个**组**。当前每组回答会复用更新 2 次，因此 `metrics.jsonl` 中奖励和组统计会重复出现；画采样趋势时只取 `rollout_update=1`，或者按新采样题组/新增生成 token 汇总。`B=1` 时单步“零方差组比例”只能是 0 或 1，至少滚动汇总几十组才有趋势意义。
`metrics.jsonl` 中 loss、ratio、熵是在该次 `optimizer.step()` **之前**计算；同一步末尾的 `dev_metrics.jsonl` 是更新**之后**的 Actor。两者要按各自时点解释。未定义的条件指标（如本批没有可提取答案时的提取后正确率）写 JSON `null`，不伪造为 0。

## 一、模型到底有没有解题进步

| 指标与状态 | 含义 | 应怎样看 |
| --- | --- | --- |
| 开发集 `pass@1`〔已有·开发/评估〕 | 每题采样 `n` 次，正确回答比例先逐题计算、再对题平均；估计随机采样一次答对的概率。 | 与训练前基座比较；同一题集、prompt、温度、回答上限、验证器和 `n`。它不是 greedy accuracy。 |
| 开发集 `pass@8`〔已有·开发/评估〕 | 每题采样 8 次，至少有一次正确的题目比例；展示模型能否采到正确答案。 | 比 `pass@1` 更依赖多次尝试；需有外部验证器才能从 8 个答案中选对，不能当作直接部署的单次成功率。 |
| 官方 test `pass@1/pass@8`〔已有·评估〕 | 最终独立评测；评估 JSON 同时保存逐题回答、奖励、长度和截断。 | 开发集选检查点之后再测。测试集结果不回流调参数。 |
| `reward_mean`〔已有·训练〕 | 当批回答奖励的平均值。当前 `math_reward` 只有 0/1，因此等于**训练题上当批采样回答的正确率**。 | 它受当批题目难度和输出格式影响，不能代替开发集准确率；将来使用连续 reward 后更不能当准确率。 |
| `reward_std`〔已有·训练〕 | 当批所有回答的奖励离散程度。 | 与 `reward_mean` 一起看；单批 `B=1,G=4` 时波动很大。 |
| 答案可提取率 `format_rate`〔已有·训练/开发/评估〕 | 回答中含合规 `\boxed{...}` 或单独 `#### ...` 的比例；也叫 `answer_extraction_rate`。 | 区分“算错了”和“没有按格式交答案”；当前未提取到最终答案就记 0 分。 |
| 格式合规后的正确率 `answer_accuracy_given_extracted`〔已有·训练/开发/评估〕 | 只在能提取最终答案的回答中计算正确比例；无可提取答案时为 `null`。 | 在同一批、且至少有一条可提取答案时，当前二元奖励满足 `reward_mean = format_rate × 合规后正确率`；可看出分数上涨是否只是学会了格式。 |
| 数据分层准确率〔已有·开发/评估〕 | 自动按 prompt token 长度档位 `0-128/129-256/257+` 与 `dataset` 来源分别报 `pass@1`；独立评估传 `--baseline-results` 时再按训练前基座的全错/混合/全对题分层。 | 避免总体上升掩盖某类题明显退步；难度分层必须基于同一数据 SHA256 和事先固定的基座结果。 |

`pass@k` 的当前实现对每题采 `n` 个答案、其中 `c` 个正确，计算 `1 - C(n-c,k)/C(n,k)` 后按题平均。最终报告应附题数、`n`、`k`、随机种子、采样设置和按题目的不确定性区间；重复生成的 8 个答案不应被当成 8 道独立题。参见 [评估实现](../evaluate.py)。

## 二、GRPO 是否真的有组内学习信号

| 指标与状态 | 含义 | 应怎样看 |
| --- | --- | --- |
| `group_reward_std`〔已有·训练〕 | 每题先算 `G` 个回答奖励的总体标准差，再按题平均。 | 接近 0 表示很多组内答案分数相同；需要看相同的是全错还是全对。 |
| `zero_variance_group_fraction`〔已有·训练〕 | 组内奖励标准差约为 0 的题目比例。对当前 0/1 奖励，包含**全错组 + 全对组**。 | 过高表示答案奖励产生的相对优势很少；仅凭此项不能判断题太难还是太简单。 |
| `all_wrong_group_fraction` / `all_correct_group_fraction` / `mixed_group_fraction`〔已有·训练〕 | 分别统计 `[0,0,0,0]`、`[1,1,1,1]`、以及同时有 0 和 1 的组。三者相加为 1；前两者之和等于当前零方差组比例。 | **混合组**才有正负相对优势。全错多时查格式、长度、基座能力；全对多时可能题太易或模型已学会。全错/全对组的 correctness policy 梯度为 0，但启用 Reference KL 时 KL 项仍可有梯度。 |
| `advantage_std`〔已有·训练〕 | 当前窗口内回答优势的总体标准差；优势由同组奖励减组均值、再除组标准差得到。 | 接近 0 常与缺少混合组一致；它不是优化器梯度范数。 |
| `mixed_group_count` / `mixed_groups_per_100_new_groups`〔已有·训练〕 | 当前新采样窗口中真正提供相对正确性信号的组数及折合每百组的数量。 | 比只看 `max_steps` 更能解释 RL 采样效率；研究 Dynamic Sampling 时尤其重要。 |

例如奖励 `[1,0,0,0]` 会产生一个正优势和三个负优势；`[0,0,0,0]` 的优势全为 0。相关计算见 [组内优势](../reasoning_forge/objectives.py)。

## 三、策略是否坍缩或偏离太快

| 指标与状态 | 含义 | 应怎样看 |
| --- | --- | --- |
| `entropy`〔已有·训练〕 | 当前 Actor 在当批已生成回答的每个有效位置，对完整词表的下一 token 概率求 `-Σ p(v)log p(v)`，再按有效 token 平均，单位是 nat。 | 反映预测分布的分散程度；它是 `detach` 的监控项，不参与当前损失。不同批次题目/前缀会变化，单条下降曲线不能证明坍缩。 |
| 固定探针熵及 p10/p50/p90〔已有·开发〕 | 在同一批开发题、同一批固定回答前缀上测熵均值与分布，保存在 `probe` 对象中。 | 排除题目/轨迹变化造成的混淆；低分位数可发现少数位置先变得极端确定。固定探针与生成多样性是两种不同测试。 |
| `final_answer_diversity` / `response_repetition_fraction`〔已有·训练/开发/评估〕 | 同一道题的 `G` 个回答中，归一化最终答案的独特数占 `G` 比例，以及全文仅合并空白后完全相同的比例。 | 熵下降且重复率升高、开发准确率下降时才像模式重复；全都答对同一个正确答案也会重复，须合看正确率。 |
| `reference_kl_k3`〔已有·训练〕 | 在已采样 token 上用 `exp(logπref-logπcurrent) - (logπref-logπcurrent) - 1` 得到的 k3 样本估计，再按有效 token 平均。 | 表示当前 Actor 偏离初始 Reference 的代理量；**不是完整词表的精确 KL**。`beta=0` 时当前代码写 0，代表没有计算这一项，不能解释为没有漂移。 |
| `ratio_mean`〔已有·训练〕 | 有效 token 上平均 `πcurrent(token)/πold(token)`；old 是本窗口采样时的 Actor。 | 首次复用更新前应约为 1。均值接近 1 仍可能同时有非常大、非常小的 ratio。 |
| `ratio_p05/p50/p95/p99` 与 `log_ratio_p05/p50/p95/p99`〔已有·训练〕 | 按当前窗口的全部有效 token 一起求分位数；观察新旧策略概率比的尾部。 | 识别“均值正常但一部分 token 偏离极大”；学习率过大或复用过多时常需看此项。 |
| `clip_fraction`〔已有·训练〕 | 对 surrogate 目标实际起裁剪作用的有效 token 比例：正优势且 ratio 超上界，或负优势且 ratio 低于下界。 | 它是**策略目标裁剪**，不是梯度裁剪。第一次复用通常约为 0；第二次以后才有机会体现 `clip_high/low` 的作用。 |
| `positive_clip_fraction` / `negative_clip_fraction`〔已有·训练〕 | 在各自正/负优势的有效 token 内，发生目标裁剪的比例；无该符号 token 时记 0。 | 做 Clip-Higher 对照时，才能知道上界改动影响了多少正优势 token。 |

看“熵坍缩”要联合判断：`entropy↓ + 固定探针熵↓ + 回答重复率↑ + 开发 pass@1↓ + 全错组↑` 才构成有力警讯。`entropy↓ + 开发 pass@1↑ + 全对组↑` 也可能是正常地变得确定。不存在适用于所有 tokenizer、提示词和温度的统一熵阈值。参见 [token 熵实现](../reasoning_forge/models.py)与 [GRPO 指标实现](../reasoning_forge/objectives.py)。

## 四、回答长度、结束方式与数据质量

| 指标与状态 | 含义 | 应怎样看 |
| --- | --- | --- |
| `response_length`〔已有·训练〕 | 回答有效 token 的平均数，包含第一次 EOS。 | 与回答上限、正确率同看；只看平均值会漏掉长尾。 |
| `response_length_p50/p90/p99`、`correct_response_length` / `incorrect_response_length`〔已有·训练/开发/评估〕 | 典型回答、长回答、极长回答分别有多长；对/错组给平均长度。 | 发现“答错题越写越长”或长度利用率偏移；做 Token-level Loss/Overlong shaping 前尤其需要。 |
| `truncated_fraction`〔已有·训练/评估〕 | 没有 EOS、且用尽 `max_new_tokens` 的回答比例。 | 升高可能表示预算不够或模型啰嗦；截断不自动代表数学答案错误，也可能在结尾前已写出答案。 |
| `truncated_unparseable_fraction` / `truncated_answer_missing_rate`〔已有·训练/开发/评估〕 | 被截断且无最终答案的回答占所有回答的比例，或占被截断回答的比例。 | 比单独的截断率更能判断是否需要加回答 token 上限。 |
| `prompt_truncation_fraction`〔已有·训练/开发/评估〕 | 题目经聊天模板渲染后超过 `max_prompt_length` 的比例。 | 若大于 0，模型可能读到残缺题目；正式训练前必须测并处理。 |
| 标准答案解析失败、训练/开发/测试题目交集〔已有·数据审计〕 | `scripts/audit_data.py` 检查当前 GSM8K 数值验证器无法解析的标准答案、重复 ID/题面与跨集交集。 | 这是 benchmark 的前置校验；指标再漂亮也无法弥补数据划分错误。 |
| 回答人工抽检〔手工〕 | `samples.jsonl` 保存每组全部 `G` 个回答及奖励、长度、截断和提取结果。 | 按组抽查“分数正确但推理胡乱”“判错但等价”“格式作弊”；程序无法代替人工判断。 |

## 五、优化稳定性与算力成本

| 指标与状态 | 含义 | 应怎样看 |
| --- | --- | --- |
| `loss`〔已有·训练〕 | 真正反传的 GRPO 目标；默认 `sequence` 口径为先按回答平均再按回答数平均。 | 主要排查 NaN/Inf 和异常跳变，不能用数值高低单独衡量数学能力。即使 loss 约为 0，梯度也可能非零。 |
| `policy_loss`〔已有·训练〕 | `-surrogate` 在有效 token 上的平均。 | 当前始终是 token 平均；默认 sequence 模式下，不一定满足 `loss = policy_loss + beta × reference_kl_k3` 的数值等式。 |
| `grad_norm`〔已有·训练〕 | `clip_grad_norm_` 返回的**裁剪前**总梯度范数。 | 持续极大或突跳需查高学习率、异常回答/ratio；它不是 LoRA 参数变化量。 |
| `learning_rate`、`step`、`rollout_update`〔已有·训练〕 | 学习率、优化器更新次数、同一采样窗口的第几次复用。 | 分开看首轮/第二轮 ratio 与 clip；不要把两次复用当作新采样两组题。 |
| NaN/Inf、OOM 事件〔已有·训练〕 | rollout/奖励、反传/优化器和开发评估发生异常时，向 `events.jsonl` 留下阶段、异常类型与信息，并继续抛错停训。 | 快速定位数值问题；不会自动恢复 OOM。按你的要求，没有加入 CUDA 峰值统计。 |
| `generated_tokens`、`prompts`〔已有·训练〕 | 新采样的有效回答 token、题目次数；同一组复用时只在第一次更新记数。 | 衡量采样预算。当前不含 prompt token、Reference 前向、开发/测试评估以及未来 Dynamic Sampling 丢弃的候选。 |
| `training_tokens/sequences/prompts`〔已有·训练〕 | 当前优化窗口实际处理的 token、回答、题目数；每次复用都会重新记。 | 衡量训练计算量；不能把它和新增生成量混为一谈。 |
| `seconds`〔已有·训练〕 | 该次更新的耗时。首次复用包含采样、打分、Reference 与训练，后续复用主要是训练。 | 比较吞吐时按完整窗口/整段运行汇总；单独比较第一次与第二次 `seconds` 不公平，另需计检查点和评估时间。 |
| 累计墙钟时间、GPU 小时及成本〔未实现〕 | 本轮按要求跳过。 | 如未来做完整成本比较，再统一计入生成、训练、评估及检查点时间。 |

## 六、复现所需的实验元数据

现有 `config.json`、`environment.json`、`data_manifest.json`、`dev_manifest.json`、`model_manifest.json`、拆分清单和 checkpoint 可记录配置、环境、数据 SHA256、模型来源及恢复位置。正式实验另需固定模型精确 revision、奖励函数版本、采样温度和上下文上限。当前训练 `samples.jsonl` 对每个新采样组保存全部 `G` 个回答及其奖励、长度、截断、题目 ID，且不依赖 `log_steps`；`dev_samples.jsonl` 保存每次固定开发评估的所有回答。两份逐题日志可能很大，应放在有足够空间的数据盘。[训练日志实现](../reasoning_forge/trainer.py)

最终作出“某改动更好”的结论时，先锁定固定开发集与最终 test 的用法；报告至少数个随机种子的结果，并在题目维度估计不确定性。训练期间优先在固定开发集上看 `pass@1`，最终 test 在选好方案后评估。

## 最小监控面板与排查顺序

1. **结果**：固定开发集 `pass@1/pass@8`、训练 `reward_mean`、格式可提取率、提取后正确率。
2. **有效信号**：全错/全对/混合组比例、`advantage_std`，按新采样题组滚动汇总。
3. **策略变化**：训练与固定探针 `entropy`、`reference_kl_k3`、ratio 分位数、`clip_fraction`、答案重复率。
4. **长度与稳定性**：回答长度 p50/p90、截断与无答案率、prompt 截断率、`grad_norm` 与 `events.jsonl`。
5. **采样规模**：累计新生成 token 与有效混合组数；不要把回答复用计为新采样。

典型排查：训练 reward 上升但开发 `pass@1` 不升，先拆格式/数学正确率，再查数据过拟合；全错组高且格式率低，先修提示词或输出预算；全错组高但格式率高，查题目难度或基座能力；KL、ratio 尾部及裁剪比例同时升高且开发成绩下降，查学习率与复用次数。策略指标和质量指标必须一起解释，单看 `loss` 或熵都不足以定性。
